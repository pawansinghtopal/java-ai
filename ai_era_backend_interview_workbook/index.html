Module 1

Deployment strategy & developer ownership

Know the options, their trade-offs, and what your team actually does.

What is a deployment strategy?

A deployment strategy defines how a new application version is introduced to an environment and its users, including availability, risk, validation, traffic shifting, and recovery.

Interview shape: name the strategy → describe the mechanics → state the benefit → state the trade-off → explain where it fits.

Deployment strategy is not the same thing as release strategy. Deployment changes the running software; release controls when a capability becomes available to users. Feature flags can decouple the two.

What is a developer's role if DevOps deploys?

DevOps/SRE/platform teams may own pipeline infrastructure and production access. Developers still help make the change deployable and safe.

  • Understand build artifacts, config, dependencies, and required migrations.
  • Ensure tests and quality gates pass; review pipeline output and release notes.
  • Coordinate approvals, deployment windows, feature flags, and backward compatibility.
  • Run or support smoke tests, watch logs/metrics, investigate regressions, and help rollback.
Don't bluff: describe only the steps you personally perform, then explain the larger process you have studied or observed.

Module 2

GitLab, branches, merge requests & CI/CD

An interviewer wants to know how your change moves safely through a team—not whether you can recite Git commands.

Typical path

issue / task
  ↓
feature branch
  ↓
commit + push
  ↓
merge request (MR)
  ↓
review + automated checks
  ↓
merge to main / release branch
  ↓
build artifact + publish
  ↓
staging / UAT checks
  ↓
approved production deployment
  ↓
smoke test + monitoring

This is a common pattern, not a mandatory GitLab workflow. Your team may use different branch names, environments, approvals, or release gates.

Branch roles (common conventions)

  • main: canonical stable branch; production-ready in many teams.
  • feature/*: isolated feature or task work.
  • bugfix/*: correction to existing behaviour.
  • release/*: optional stabilization branch for a planned release.
  • hotfix/*: urgent production fix, usually based on the released production version.
  • develop: integration branch in some Git Flow-style teams; not universal.
A branch named uat or prod is a team convention—not a GitLab requirement. Many web-service teams deploy the same commit or artifact through environments instead.

GitLab vocabulary you should be able to explain

Branch

A movable reference to a line of development. It is not itself a release or deployed environment.

Commit

A recorded snapshot/change in repository history, identified by a hash.

Merge request

A review and collaboration mechanism for discussion, approvals, and checks before merging.

Pipeline

Jobs and stages automated by CI/CD configuration, for example build, test, scan, package, deploy.

Artifact

A build output, such as a JAR or container image, that downstream jobs can use.

Environment

A deployment target such as development, staging, UAT, or production, tracked in GitLab where configured.

Module 3

Versioning, tags, releases & rollback

Semantic Versioning

For a public API/library that follows SemVer, the familiar format is MAJOR.MINOR.PATCH.

  • Major: incompatible public API change.
  • Minor: backward-compatible functionality.
  • Patch: backward-compatible bug fix.
1.4.2 → 1.4.3  bug fix
1.4.3 → 1.5.0  compatible feature
1.5.0 → 2.0.0  breaking change

A team's internal application build number may follow different rules. Don't claim every commit increments a semantic version.

Tag vs release vs branch

  • Branch: moves as new commits are added.
  • Tag: names a specific commit; release tags often use annotated tags.
  • Release: a published release record with a version, notes, and often links/artifacts.
  • Build number: identifies a pipeline/build run; not always the user-facing product version.
  • Artifact/image tag: version or commit identifier used to find the exact built output.
A strong release process can answer: “Exactly which commit, artifact, config, and database state are in production?”

Module 5

Context windows, retrieval & hallucinations

What is a context window?

The model's working token budget for the current interaction. It can include your prompt, chat history, code snippets, retrieved files, tool output, and room for generated output.

Important: opening a repository in an AI IDE does not mean the model has read every file. The tool may index/search the codebase and select relevant pieces; irrelevant or missing context can change the answer.

More context is not always better. A smaller, relevant set of files and a clear goal can outperform pasting a huge repository dump.

What is hallucination?

A model produces confident-sounding but false or unsupported content. In coding, that can mean inventing a class, method, configuration key, framework behaviour, API field, or test result.

Why it happens: generative models predict plausible continuations; they don't guarantee factual verification. Missing context, ambiguous prompts, uncommon APIs, stale knowledge, and pressure to provide a complete answer can contribute.

NIST uses “confabulation” for confidently stated but erroneous or false generated content—commonly called hallucination.

How to reduce risk in practice

Ground the answer

Give relevant files, exact logs, API contracts, schema, framework version, and reproducible steps.

Ask for evidence

Request real file paths, method names, specific assumptions, and the source of each key claim.

Verify independently

Compile, test, inspect diffs, check official docs, examine DB plans, and run safe benchmarks.

Module 6

A safe, repeatable AI-assisted engineering workflow

A practical process for using AI without outsourcing engineering judgement.

Before asking AI to code

  1. Understand the bug/requirement and success criteria.
  2. Trace the current flow through controller, service, repository, integrations, config, and tests.
  3. Provide relevant files, versions, logs, and constraints.
  4. Ask for a plan and failure modes before broad edits.

Before accepting the result

  1. Read every changed line and understand why it changed.
  2. Build and run relevant tests; verify test coverage is meaningful.
  3. Inspect exception handling, auth, validation, transactions, retries, timeouts, and resource limits.
  4. Check SQL/query count, latency implications, backward compatibility, and deployment requirements.
  5. Review diff, commit cleanly, and be able to explain the design in a code review.
Never paste production secrets, customer personal data, credentials, private keys, or restricted code into an AI tool unless your organization's approved policy explicitly permits that use. Follow team rules for data retention, privacy, and model access.

Use AI to challenge the change, not just write it

Review this diff as a skeptical senior engineer. Do not rewrite it yet.
Look for:
- correctness and backward compatibility
- race conditions and data consistency
- transaction/rollback behaviour
- N+1 queries, connection-pool pressure, memory/CPU costs
- timeout/retry amplification and duplicate side effects
- authentication, authorization, injection, and sensitive logging
- missing tests and observability
For every concern, point to a changed line and explain how to reproduce or test it.
Separate confirmed defects from hypotheses.

Module 8

Current-project audit checklist

Fill this out from your actual repository, pipeline, runbooks, and teammates. An interviewer may ask follow-ups that expose whether you understand the real process, so don't answer from assumptions.

A credible way to describe limited deployment ownership

Use your own facts, but follow this structure:

“In my current project, the DevOps/platform team owns [accurate portion of pipeline or production access]. My contribution is [specific actual responsibilities, such as preparing the change, ensuring tests pass, reviewing logs, coordinating UAT, validating endpoints, or supporting production verification]. I understand the release flow from [actual trigger] through [actual gates] to [actual deployment mechanism]. After deployment, we validate [specific health checks] and if [specific failure condition] occurs, our rollback/recovery approach is [known procedure]. I haven't personally owned [thing you haven't done], so I wouldn't claim that—but I know where my team's responsibility begins and ends.”

Don't memorise this with invented details. Replace every bracket with evidence from your own system.
